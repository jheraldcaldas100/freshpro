> **Estado:** especificación v1.0 (2 rondas con Codex). **Aprobada.** Hosting elegido: **Render (web, gratis hasta F5) + Neon (PostgreSQL)**.
> **Fase siguiente:** F1 — Catálogo y contenido.

## 1. Objetivo

Un proyecto Django vacío pero real: se levanta en local en minutos, cada push pasa por controles automáticos y existe una URL pública con HTTPS. Ninguna funcionalidad del producto todavía.

## 2. Alcance

### Incluye

1. **Proyecto Django en la raíz del repositorio**
   - Python **3.12** (fijado en `.python-version`), **Django 5.2 LTS**.
   - Dependencias con **uv**: `pyproject.toml` + `uv.lock` versionado. Grupos: producción (`django`, `gunicorn`, `whitenoise`, `dj-database-url`, `psycopg[binary]`) y desarrollo (`pytest`, `pytest-django`, `ruff`, `python-dotenv`).
   - Todos los comandos se ejecutan con `uv run` (local y CI), sin activar entornos a mano. En CI se usa `--locked` (falla si `uv.lock` no coincide con `pyproject.toml`); en Docker y `start.sh`, `--no-sync` después de instalar, para no reinstalar el grupo dev ni tocar el entorno como usuario no root.
   - Estructura (§5.3):
     ```
     manage.py
     config/            settings/{base,dev,prod}.py, urls.py, wsgi.py
     core/              página de inicio y /salud/
     catalogo/ perfiles/ feed/ entrevistas/ eventos/   (apps vacías, registradas)
     templates/base.html, templates/core/inicio.html
     assets/app.css (fuente Tailwind) → static/css/app.css (compilado)
     tests/
     analisis/          (vacío, con .gitkeep)
     ```
   - Idioma y zona: `LANGUAGE_CODE="es-pe"`, `TIME_ZONE="America/Lima"`, `USE_TZ=True`.

2. **Configuración por entorno**
   - `config.settings.dev` por defecto en `manage.py`; `config.settings.prod` en el servidor (`DJANGO_SETTINGS_MODULE`).
   - Variables de entorno: `SECRET_KEY`, `DATABASE_URL`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `ADMIN_URL`.
   - **dev:** `DEBUG=True`, `SECRET_KEY` de desarrollo, `DATABASE_URL` opcional (por defecto SQLite en `db.sqlite3`). **Carga `.env` automáticamente** con `python-dotenv` si existe; al arrancar muestra qué base de datos está usando, para que nadie trabaje contra SQLite creyendo usar PostgreSQL. Prod **nunca** lee `.env`.
   - **pytest** usa `config.settings.dev` (fijado en `pyproject.toml`, `[tool.pytest.ini_options]`); en CI, `DATABASE_URL` apunta al PostgreSQL del servicio.
   - **prod:** falla al arrancar si falta `SECRET_KEY`, `DATABASE_URL` o `ALLOWED_HOSTS`. `DEBUG=False`, `SECURE_PROXY_SSL_HEADER`, `SECURE_SSL_REDIRECT`, cookies de sesión y CSRF seguras, HSTS de 1 hora (se sube después del demo), WhiteNoise con archivos comprimidos y con hash.
   - `.env.example` con todas las variables y sin valores reales. `.env` en `.gitignore`.

3. **Rutas**
   - `/` — página de inicio mínima, móvil primero, con Tailwind: nombre "Oppu" y la propuesta de valor. Sirve para verificar plantillas, CSS y estáticos.
   - `/salud/` — responde `200 {"estado": "ok"}` si la base de datos responde (`SELECT 1`), `503` si no. La usa el hosting como health check. La atiende un **middleware al inicio de la cadena** (`core.middleware.SaludMiddleware`), antes de la validación de host y de la redirección a HTTPS: la sonda del hosting llega por HTTP interno y con un Host propio, y la respuesta es fija y no expone datos.
   - `/<ADMIN_URL>/` — admin de Django en una ruta configurable (por defecto `admin/` en dev).

4. **Tailwind sin Node**
   - Script **en Python** `scripts/tailwind.py` (funciona en Windows, macOS y Linux) que descarga el CLI standalone de Tailwind en una **versión fijada** y para el sistema operativo correspondiente a `bin/` (ignorado por git), y compila `assets/app.css` → `static/css/app.css`. Opción `--watch` para desarrollo.
   - El CSS compilado **se versiona**, para que el despliegue no dependa de descargar el CLI. CI lo recompila y falla si difiere del versionado (así no se desfasa de las plantillas).

5. **Calidad local y en CI**
   - `ruff check` y `ruff format --check`.
   - `pytest` con `pytest-django`.
   - **GitHub Actions** (`.github/workflows/ci.yml`) en cada push y pull request:
     1. `uv sync --locked`;
     2. `uv run --locked ruff check .` y `uv run --locked ruff format --check .`;
     3. `uv run --locked python manage.py makemigrations --check --dry-run`;
     4. `uv run --locked pytest` contra un servicio **PostgreSQL 16**, igual que producción;
     5. `uv run --locked python manage.py check --deploy --fail-level WARNING` con settings de prod y variables ficticias (las excepciones deliberadas, si las hay, se silencian en settings con un comentario que explique por qué);
     6. `uv run --locked python scripts/tailwind.py` y `git diff --exit-code static/css/app.css`;
     7. `docker build` de la imagen.

6. **Despliegue**
   - **Dockerfile** (`python:3.12-slim` + uv): instala dependencias congeladas (sin el grupo dev), ejecuta `collectstatic` en la construcción y corre como usuario no root.
   - `collectstatic` en la construcción usa settings de prod con **valores ficticios solo para ese comando** (`SECRET_KEY=build-only`, `DATABASE_URL=sqlite:///:memory:`, `ALLOWED_HOSTS=localhost` en la misma línea `RUN`), sin conectarse a PostgreSQL y sin dejar esos valores en la imagen: al arrancar, prod sigue exigiendo las variables reales.
   - `.dockerignore` excluye `.git`, `.env`, `.venv`, `db.sqlite3`, `bin/` y cachés.
   - `scripts/start.sh`: `migrate --noinput` y luego `gunicorn config.wsgi` en el `$PORT` del hosting. Migrar al arrancar es aceptable porque el demo corre con **una sola instancia**.
   - Plataforma recomendada: **Railway** (app + PostgreSQL en el mismo proyecto y sin suspensión; plan Hobby, unos 5 USD al mes). Revisar si la cuenta nueva trae crédito de prueba; si no y el equipo prefiere no pagar todavía, usar **Render gratis hasta F5** (aceptando que se duerme) con la base en **Neon** (plan gratuito, no expira; la PostgreSQL gratuita de Render expira a los 30 días), y pasar el servicio web a un plan pagado antes de F6. El Dockerfile funciona en ambas.
   - Health check apuntando a `/salud/`.
   - `render.yaml` (Blueprint) con el servicio web Docker, `healthCheckPath: /salud/` y las variables a completar. En prod, si existe `RENDER_EXTERNAL_HOSTNAME` (la define Render), se agrega automáticamente a `ALLOWED_HOSTS` y a `CSRF_TRUSTED_ORIGINS`.

7. **Documentación**
   - `docs/DESARROLLO.md`: requisitos, levantar el proyecto en local paso a paso, compilar CSS, correr pruebas y lint, variables de entorno, cómo desplegar.
   - `README.md` corto: qué es Oppu y enlaces a los documentos.

### No incluye

- Modelos, pantallas del producto, autenticación de estudiantes (F1 en adelante).
- Dominio propio, monitoreo, copias de seguridad automáticas (se configuran antes de F6, §5.4).
- Más de una instancia del servidor.

## 3. Pruebas automáticas

| Prueba | Qué comprueba |
|---|---|
| `test_inicio` | `/` responde 200, usa `core/inicio.html` y enlaza `css/app.css`. |
| `test_salud_ok` | `/salud/` responde 200 y `{"estado": "ok"}`. |
| `test_salud_sin_bd` | Si la consulta a la base falla, `/salud/` responde 503 (simulado). |
| `test_admin_pide_login` | La ruta del admin redirige al login sin sesión. |
| `test_admin_url_configurable` | Con `ADMIN_URL` distinto, el admin está ahí y no en `admin/`. |
| `test_prod_exige_variables` | Importar settings de prod sin `SECRET_KEY` (o sin `DATABASE_URL`, o sin `ALLOWED_HOSTS`) lanza un error claro. |
| `test_prod_seguro` | Con variables completas, prod tiene `DEBUG=False`, cookies seguras y redirección a HTTPS. |
| `test_prod_salud_sin_redireccion` | Con settings de prod, una petición HTTP a `/salud/` con `Host: healthcheck.railway.app` recibe 200 (no 301), mientras que una petición HTTP a `/` recibe 301 a HTTPS. |
| `test_dev_carga_env` | Con un `.env` temporal, dev toma `DATABASE_URL` de ese archivo. |
| `test_apps_registradas` | Las 5 apps del producto están en `INSTALLED_APPS`. |

## 5. Qué necesita el equipo (no lo puede hacer Claude)

- Crear la cuenta en **Railway** (o Render), conectar el repositorio de GitHub y crear la base PostgreSQL.
- Cargar las variables de entorno en la plataforma (Claude indica cuáles y cómo generar `SECRET_KEY`).
- Crear el superusuario en producción: desde la consola de Railway, o —si se usa Render gratis, que no tiene consola— ejecutando `createsuperuser` en local con settings de prod y la `DATABASE_URL` externa de la base (procedimiento en `DESARROLLO.md`).

## 6. Riesgos

| Riesgo | Mitigación |
|---|---|
| El CLI de Tailwind no se puede descargar en la máquina de un integrante. | El CSS compilado está versionado: solo hace falta para cambiar estilos. |
| Integrantes con Windows. | Todo se ejecuta con `uv run` y scripts en Python, sin bash. V2 se hace, si es posible, con alguien que use Windows. |
| Diferencias entre SQLite (local) y PostgreSQL (prod). | CI corre las pruebas en PostgreSQL. |
| Migrar al arrancar con varias instancias. | Una sola instancia, documentado. Si se escala, mover a un paso previo al despliegue. |

## 7. Cambios durante la implementación

- **Fuente de Tailwind en `assets/`** (no en `static/src/`): `collectstatic` con el almacenamiento de producción intentaba procesar `@import "tailwindcss"` y fallaba, lo que habría roto la construcción de la imagen. Se agregó la prueba `test_collectstatic_de_produccion`.
- **`/salud/` como middleware** en lugar de `SECURE_REDIRECT_EXEMPT` + host en `ALLOWED_HOSTS`: funciona igual en Render y Railway sin conocer el Host de la sonda.
- **`ADMIN_URL` obligatoria y distinta de `admin/` en producción** (prueba `test_prod_rechaza_admin_obvio`).
- **`security.W021` silenciado** con justificación (no se pide precarga HSTS para un subdominio temporal).
